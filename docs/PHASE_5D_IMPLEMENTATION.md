## 1. Alcance y fronteras

- D01–D12, inseparables para el cierre: importar `.mrpack` local, desde URL HTTPS autorizada o desde proyecto/versión Modrinth, inspeccionar antes de instalar, crear instancia nueva sin publicar incompleta, instalar archivos y capas cliente verificadas, guardar identidad/base, actualizar mediante comparación base/local/nuevo, exportar `.mrpack` interoperable y recuperarse de fallos/interrupciones. Todo operable dentro de la TUI; ninguna descarga terminada debe disparar Play.
- Soporte inicial de runtime: **Vanilla o Fabric con versión exacta**. No convertir Forge/NeoForge/Quilt a Vanilla/Fabric. Si una versión de pack cambia Minecraft o loader, la instancia gestionada actual no admite mutar esas identidades: bloquear actualización in-place y ofrecer instalación como instancia nueva (migración de datos solo mediante flujo explícito). Las dependencias del índice son del *runtime*, no dependencias de mods de API.
- Importar ZIP genérico, instancias Prism/MultiMC, CurseForge, publicación autenticada en Modrinth y nuevos loaders pertenecen a 5E/no son soporte implícito. Recursos y shaders pueden venir como *archivos de pack* en `resourcepacks/` y `shaderpacks/`, aunque sus paneles de gestión separados figuran en E06; no mezclar estado del panel 5C con la identidad del pack. No meter recursos/shaders implícitamente en Reset Configs.
- No prometer instalación universal: un pack con loader, URLs, permisos, tamaños o contenido no soportados se bloquea con causa/archivo exactos antes de activar una instancia. La instalación heredada `legacy` no es destino de importación/actualización automática: crear una instancia gestionada nueva.

## 2. Formato real y discrepancias a resolver

Fuente normativa: [especificación Modrinth `.mrpack`](https://support.modrinth.com/en/articles/8802351-modrinth-modpack-format-mrpack). ZIP `.mrpack` con `modrinth.index.json` UTF-8 en raíz, `formatVersion` numérico (documentado: 1), `game: "minecraft"`, `versionId` (identificador **interno del índice**, no ID de versión API), `name`, `summary?`, `files[]` y `dependencies` (`minecraft`, `fabric-loader`, `forge`, `neoforge`, `quilt-loader`; pueden añadirse claves). Cada entrada declara `path` relativa a `gameDir`, `hashes.sha1` y `hashes.sha512` obligatorios, `downloads[]` URLs HTTPS, `fileSize` bytes, `env?` con `client`/`server` ∈ {`required`, `optional`, `unsupported`}. El servidor referido es el dedicado: omitir `unsupported` para cliente; preguntar por `optional`; ausencia de `env` no implica exclusión cliente. Rechazar esquema/clave de runtime desconocida en vez de ignorar dependencias que podrían cambiar el juego.

Instalación cliente: archivos descargados elegidos del índice; luego `overrides/`, luego `client-overrides/` sobre la misma ruta final; **nunca** `server-overrides/`. Inventariar el resultado de capas por ruta, incluyendo hashes y origen; una superposición declarada entre capas es intencional, no una colisión arbitraria. Colisión entre `files[]` o entradas duplicadas dentro de una capa: error. Archivo del índice tapado por override: no dejar un archivo descargado ignorado sin reportarlo; definirlo explícitamente en el plan e inventario.

- La especificación de subida de Modrinth acepta `cdn.modrinth.com`, `github.com`, `raw.githubusercontent.com`, `gitlab.com` para `downloads` y exige HTTPS. Recomienda seguir al menos tres redirecciones 3xx; aplicar política propia de hosts exactos y validar **cada salto**, no seguir redirects a LAN o HTTP. Esta lista de aceptación de subida **no** constituye permiso de redistribución ni obligación de confiar en cualquier URL dentro del dominio. [Formato](https://support.modrinth.com/en/articles/8802351-modrinth-modpack-format-mrpack).
- **Desajuste explícito de DEC-10:** §10.18 del plan describe `api.modrinth.com`/`cdn.modrinth.net`, 250 MiB por `.jar` y 10 MiB por JSON de API; el código de `internal/modrinth/client.go` permite `cdn.modrinth.net` y `cdn.modrinth.com` para binarios. GitHub/GitLab del formato no están autorizados por ese cliente; `Stage` en `internal/modrinth/download.go` es para un JAR Modrinth, no para todo `.mrpack` ni para recursos/configuraciones. **Decisión antes de D01/D02:** ampliar explícitamente la política 5D con hosts autorizados y redirecciones verificadas (o documentar packs no instalables y bloquearlos), sin degradar 5C. Revisar también la semántica de redirecciones al iniciar en `.com` y evitar SSRF con destinos IP/loopback/metadata y resoluciones cambiantes. No exponer tokens ni solicitudes a hosts de terceros.
- Presupuestos distintos por: ZIP comprimido, número/profundidad de entradas, índice JSON, expansión total y por archivo, número y bytes de descargas declaradas, nombres/longitud de rutas, espacio disponible y salida `.mrpack`. Propuesta a validar con packs reales: ZIP ≤ 512 MiB, índice ≤ 8 MiB, ≤ 8192 entradas, expansión ≤ 2 GiB, override individual ≤ 256 MiB, descargas agregadas ≤ 4 GiB; el límite 250 MiB/JAR de 5C se conserva para JARs bajo esa ruta hasta decisión expresa. Los números son **propuesta**, no límites del formato ni decisión adoptada; elegir y registrar cotas con casos válidos antes de codificar. Contabilizar bytes de stream incluso si `Content-Length` falta o miente, y verificar ZIP CRC además de hashes de archivos descargados. No descomprimir el ZIP entero en memoria.

## 4. Flujos de implementación

### 4.1. Importar (D01–D07, D12)

1. Elegir archivo local `.mrpack` o proyecto/versión de catálogo; capturar versión de API (IDs de proyecto y release) solo si la fuente es Modrinth. Descargar pack de API bajo límite separado y verificar hash del *archivo pack* según metadata de esa release. Un archivo local puede carecer de identidad API y aun así ser importable y exportable; para **actualización automática** exigir identidad API inequívoca o nuevo `.mrpack` aportado por el usuario.
   Una URL directa de `.mrpack` también requiere whitelist, redirecciones controladas, tope de archivo, `Content-Type`/contenido y hash calculado localmente; sin hash esperado independiente no se puede afirmar autenticidad del pack, solo integridad de lo recibido y de los archivos descargados respecto de ese índice. Advertir al usuario y no atribuir identidad API a una URL. No guardar URLs con tokens/query sensible en metadata o logs.
2. Preflight ZIP/índice sin escribir en `gameDir`: formato/UTF-8/campos/JSON, hash/size, runtime exacto, ruta portable y segura para cada entrada y capa, duplicados, URL host/política/redirect, presupuesto de recursos. Reconocer solo índice y directorios de overrides; rechazar contenido raíz inesperado con diagnóstico en vez de ejecutarlo. Aceptar `env.client=optional` con selección explícita persistida. Mostrar nombre, `versionId`, Minecraft/loader exacto, archivos requeridos/opcionales/omitidos, descargas y tamaños conocidos, overrides y permisos/advertencia de ejecución de mods.
3. Revisar y confirmar nombre/Java/memoria de instancia nueva y lista de opcionales. Reservar ID no visible; crear directorio privado en el **mismo filesystem** del destino final, mantener journal de progreso. Descargar todos los `files[]` elegidos a temporales con `context.Context`, streaming, SHA-1 y SHA-512, size exacto y status; varias URLs solo como alternativas validadas. Aplicar capas con validación de rutas y presupuesto; inventariar contenido *final* con hashes; preparar runtime Minecraft/Fabric exacto sin Play.
4. Escribir `instance.json`, `pack.json` y `mods.json` coherentes y fsync de archivos/directorio según plataforma antes de publicar. Revalidar que ID final sigue libre; renombrar el directorio privado como `instances/<id>` únicamente tras éxito de la instalación. Listar/seleccionar instancia después de publicar, nunca antes; no borrar restos sin confirmar si hay interrupción ambigua. Mantener el área privada para recuperación/limpieza identificable y acotada.

**Seguridad de rutas:** normalizar separadores ZIP/índice (`/`) y rechazar absolutas POSIX/Windows, drive/UNC, `..`, `.`, componentes vacíos, NUL/control, nombres reservados Windows, sufijos espacio/punto, segmentos especiales y colisiones sin distinción de case en sistemas objetivo; limitar profundidad/longitud. Rechazar entradas ZIP que no sean archivos/directorios regulares (symlinks, junctions, modos especiales), entradas cifradas, duplicadas o que apunten fuera. Antes de crear/copiar y antes de publicar, `Lstat` de cada ancestro y destino para no seguir enlaces, también en actualizaciones con carpetas preexistentes. Evitar `filepath.Clean` como sustituto de validación previa; reconstruir la ruta bajo raíz controlada y comprobar contención.

### 4.2. Identidad y manifiesto base (D07)

`pack.json` **propuesto** al lado de `instance.json`, schema versionado y escrituras seguras: `source` (`modrinth` + `project_id` + `version_id` API, `local` o `url` autorizada sin secretos), `index_version_id`, `index_sha512`, runtime exacto, opciones de cliente seleccionadas y por ruta relativa final `base_sha512`, tamaño, capa (`downloads`/`overrides`/`client-overrides`), fuente verificable (URL/ID/hash cuando proceda). No guardar secretos ni URLs con credenciales/query sensibles; separar identidad de origen de URLs que podrían caducar. La base representa bytes instalados al cerrar cada versión, **no** el estado actual del disco: nunca reemplazarla por hashes locales durante una exploración. Leer `mods.json`/archivos reales para detectar ediciones y mods externos. Definir migración/errores explícitos ante schema desconocido, pérdida de registro y packs locales no identificables; no inventar una base a partir del disco alterado.

### 4.3. Actualizar sin borrar cambios (D08–D09, D12)

- Obtener versión elegida de *ese proyecto* (no asumir «latest» ni que el `versionId` interno es ID API), descargar/verificar nuevo pack; preflight runtime/capacidades. Puede ofrecerse `.mrpack` local como nuevo origen con confirmación si la identidad API falta. Requerir instancia managed con `pack.json` válido y ruta no compartida; abortar si cambian Minecraft/loader exactos. Renovar selección de opcionales si cambian.
- Para cada ruta de la **unión** entre base anterior, disco local y base nueva, comparar por bytes hash, no por mtime. Clasificar: añadido nuevo, eliminado upstream, reemplazo upstream, igual upstream, agregado local, modificado local, eliminado local y conflictos simultáneos; no confundir un `mods/` externo ni un `options.txt` con archivo propio. `new == old` → mantener local; `local == old` → aplicar nuevo o retirar; `local != old` → conservar local por defecto y exigir decisión **por ruta** para sobrescribir/quitar, incluyendo ausencia local. Si aparecen `new == local`, registrar nueva base sin copiar. Dos fuentes nuevas para un mismo destino = preflight fallido salvo prioridad documentada de capas. Presentar totales y conflictos por ruta con opción conservar/sobrescribir/omitir actualización; si conservar local, guardar base **nueva** separada del hash local para que la próxima actualización siga detectando divergencia. No fusionar automáticamente textos/configuración.
- Descargar/verificar plan íntegro fuera de rutas activas; tras confirmación y bajo lock de instancia, recalcular hashes/colisiones y espacio (revisión puede quedar obsoleta). Journal persistente antes de mutar, copia/renombrado de versiones anteriores al respaldo privado con cuota y regla de retención **específica de packs** a decidir; no aplicar la cuota «1 JAR o 500 MiB» de DEC-06 a mundos/config completos. Publicar archivos y manifest/registro de manera recuperable, no afirmar que múltiples `os.Rename` son una transacción. Ante caída: recovery idempotente en arranque/antes de Play, terminar o revertir con evidencia; si recuperación falla, bloquear instancia e informar rutas y pasos de restauración, nunca mostrar éxito. No borrar saves, logs, credenciales o archivos externos.

### 4.4. Exportar `.mrpack` interoperable (D10–D12)

- Elegir instancia managed, nombre y `versionId` interno (no confundir con ID API), snapshot bajo lock; decidir explícitamente qué configuraciones, `options.txt`, recursos/shaders y otros archivos de autor incluir como overrides. Excluir de forma predeterminada mundos/`saves`, logs, cachés, runtime, backups, metadata interna (`instance.json`, `mods.json`, `pack.json`), lock, cuentas/tokens, claves y rutas privadas. Evaluar contenido sensible también en archivos seleccionados: filtro automático no garantiza detectar secretos; mostrar rutas y advertencia antes de exportar. Nunca empaquetar JAR ajeno local por defecto.
- Por cada artefacto del inventario (incluidos mods, recursos y shaders), construir `files[]` con URLs directas HTTPS permitidas para ese **archivo exacto**, hashes SHA-1/SHA-512 y bytes revalidados contra disco; o, solo con permiso probado y consentimiento explícito, incluir bytes en `overrides/`. La [guía de permisos Modrinth](https://support.modrinth.com/en/articles/8797527-obtaining-modpack-permissions) distingue archivo alojado en Modrinth de otro release del mismo proyecto; una URL válida no prueba licencia. Si no hay fuente o autorización verificable, **reportar por ruta y bloquear exportación completa** (o exigir exclusión explícita, indicando que cambia el pack), nunca omitir silenciosamente ni inventar una URL. Para subir luego a Modrinth verificar además su whitelist efectiva y términos; subir/publicar no forma parte de D10.
- Escribir ZIP temporal con `modrinth.index.json` UTF-8 raíz, `formatVersion: 1`, `game: minecraft`, dependencias runtime soportado, `files` y `overrides`/`client-overrides` seleccionados; `env.client` reflejar opcionales soportados. ZIP cerrado, sync y renombrado al destino elegido solo después de éxito. Importar el **artefacto recién generado** en raíz temporal aislada y comparar lista de rutas/hashes/opciones cliente para probar round-trip; confirmar exportación únicamente si se puede reimportar. Evitar usar la instalación real para esa validación.

## 5. TUI: recorrido mínimo verificable

- **Flujo final de navegación decidido:** en el menú de inicio, el botón/opción se llama **Modrinth**. Al pulsar **Enter** se abre su submenú con **Mods**, **Resource Packs** y **Shaders**; al implementar 5D se agrega **Modpacks** en ese mismo submenú. No agregar «Modpacks» como acceso independiente del menú de inicio ni reemplazar la entrada «Modrinth» por «Mods».
- Desde **Modrinth → Modpacks**: importar archivo local o URL HTTPS autorizada o buscar packs Modrinth (`project_type=modpack`), ver detalle/versión, preflight, opciones cliente, revisión de destinos/espacio, confirmación, progreso bytes conocidos o spinner, resultado y selección manual de instancia; actualizar pack de la instancia y exportar desde la misma sección. No asumir que agregar búsquedas de `mod`/`resourcepack`/`shader` a 5C resuelve búsqueda `modpack`: los filtros de loader y versión y el archivo elegido son diferentes.
- Estado de cada tarea con request ID, `context` cancelable y destino capturado; descartar respuestas tardías de búsqueda, no salir de publicación/rollback hasta estado seguro. Vista de conflictos y permisos con scroll, rutas largas y nombres externos sanitizados (secuencias de control), foco y teclado, errores por archivo y posibilidad de reintentar sin éxito falso. Mostrar claramente «no soportado» frente a «descarga fallida»; no ofrecer Play sobre staging.
- Revisar `screenState` y condiciones por rangos en `model.go`, `update.go`, `view.go`, `styles.go`, menú/barra/footer y catálogos i18n español/inglés. Reusar patrones de progreso/cancelación del catálogo 5C sin acoplar packs al estado de instalación de un mod. Salida y recuperación accesibles tras reiniciar la TUI.

## 6. Plan incremental y pruebas que sí prueban comportamiento

| Corte | Entrega | Criterios del plan |
| --- | --- | --- |
| Preflight | Parser ZIP/índice + política hosts/límites/resolución runtime + pantalla de revisión, sin tocar instancias | D02, D03, D06 |
| Importación | origen local/catálogo autorizado, staging privado, descarga verificada, capas y metadata publicada | D01, D04, D05, D07 |
| Actualización | identidad + comparación de tres estados + consentimiento por conflicto + journal y recovery | D08, D09, parte de D12 |
| Exportación | inventario/permiso, ZIP portable, reimportación de bytes y manifest, errores sin pérdida | D10, D11, resto de D12 |

Pruebas deterministas con `archive/zip`, `httptest` y `t.TempDir` (sin tocar `.minecraft` real): formato válido Fabric y Vanilla, cliente opcional/no soportado; falta loader/versión exacta; sha1/sha512/size corruptos, HTTPS y redirecciones prohibidas, 429/truncado; traversal `../`, ruta Windows absoluta/UNC, `%` o caracteres hostiles, enlaces, nombres reservados, colisión case-fold y entre capas, ZIP bomb/índice gigante/CRC; `server-overrides` nunca en cliente; error y cancelación en cada etapa sin entrada listada; interrupción real entre publicación de archivos y manifest con reinicio y recovery; dos procesos bajo lock y cambios externos posteriores a la revisión; 3-way para config editada, borrado local, archivo nuevo, reemplazo upstream, resultado conservado en siguiente update; cambio de Minecraft/loader bloqueado; exportar con mod sin fuente/permiso y con secreto, reproducir dos instancias aisladas desde pack exportado con hashes/opciones idénticos. Verificar manualmente flujo interactivo en Linux y, cuando sea posible, Windows/macOS reales: antivirus/archivos abiertos, Unicode/rutas largas, sesiones simultáneas y cancelación; compilación cruzada no prueba ejecución. No usar tests que solo comprueban que se llaman wrappers o que se genera un ZIP no vacío.

## 7. Decisiones abiertas y riesgos antes de codificar

1. Aprobar política de hosts/redirects de archivos del índice y packs remotos, reconcile DEC-10 con formato oficial; definir si GitHub/GitLab entran y cómo se restringen IP/SSRF. Sin ello no es honesto declarar D01 universal para `.mrpack` válido.
2. Fijar límites propios para pack/ZIP/expansión/descarga y cuota de backups; límites 5C por JAR/API no alcanzan. Medir packs de prueba representativos antes de escoger cotas definitivas.
3. Acordar dónde se publica una instancia nueva y política de huérfanos/rollback/retención tras fallo, y quién bloquea Play cuando hay recovery pendiente. `Create` actual la hace visible de inmediato.
4. Resolver relación pack-owned vs gestión individual 5C (activar/desactivar/actualizar/eliminar JAR o recurso): tratarlo como divergencia local y advertir antes de sustituir; pack nunca puede asumir posesión de archivos externos.
5. Acordar garantías de permiso exportable y qué hacer con archivos sin URL exacta/licencia; separar exportación local de publicación en Modrinth y de validación legal. Revisar permisos en el momento de distribuir, no inferirlos de hashes o proyecto.
6. Acordar expectativa para cambio de runtime de pack: instancia nueva recomendada por `UpdateSettings` fijo. No intentar migrar mundos/config automáticamente.
